# 文档维护规则

## 文档的三层职责

1. Planning：产品总设计，按 UI、数据结构、功能展开，说明现状及后续。
2. 专题设计：某个页面、数据契约或功能的完整现行规则，包含对象结构、行为、边界和代码入口。
3. 修改日志：某轮需求、问题、取舍、改动及验证的过程证据，允许按时间追加。

不能用日志末尾的新段覆盖前文旧规则，也不能让读者先通读所有聊天才能得知当前设计。专题可保留兼容规则，但应说明“新行为 / 旧数据兼容”，而非并列两套互相冲突的现行要求。

## 每轮修改的工作方式

先读 Planning、对应主题和实际代码，确认现行规则与用户新要求。更新所属章节的结构、行为、限制及例子，删除或明确迁移被替代描述；跨模块变更同步改相关摘要和链接。

随后写修改日志，记录需求/问题、最终行为、必要取舍、影响范围与真实验证。测试数、截图尺寸、构建结果、exe 替换状态写入日志；长期约束和验收方法写入设计。没有执行的验证必须说清楚，不复制旧结果当本轮结果。

保存前检查链接、锚点、类型名和代码入口，检查 Planning 与专题是否一致。只有日志能持续按时间追加，设计不使用“最新某段优先”规则。

## 状态与边界

- 已实现：代码路径存在，并说明对应数据/接口/UI 行为。
- 兼容：解释保留哪些旧数据与行为、新建对象采用什么规则。
- 待实现：明确入口是否仅预留、哪些服务/渲染/协议尚未完成。
- 待验收：实现或模拟验证存在，但真实服务/桌面交互未验证。

用户确定的思想与代码有差距时，写“设计要求”及“当前实现边界”，不要把旧代码误写成用户选择，也不要未经验证宣称目标全部完成。

## 修改日志条目格式

```markdown
## 功能名称 / 本轮修改

需求或问题：说明触发场景和目标。

修改：描述最终行为、相关数据和必要取舍。

设计归属：链接到更新后的规范章节。

验证：真实执行的检查、结果和未验证范围。
```

同日多轮按顺序追加独立条目。没有可靠轮次/日期的旧记录按来源归档并注明，不补造聊天顺序。自动测试通过、编译通过、浏览器观察、桌面验收、真实模型/GPU 联调分别记录，不能相互代替。

## 历史材料与上下文交接

重整前原文位于 changelog/archive，manifest.json 记录源文件、字节数和 SHA256。原文不修改，包含当时的矛盾描述与验收数字；它们只能作为修改日志历史材料引用。根目录 Planning - 副本.md 保留原始规划，亦不作当前验收标准。

切换上下文后先读总体设计、专题和能力边界；只有追查改动原因/验证证据时读日志。交接说明指出“当前规则在哪、做到了什么、缺什么”，不再重抄整段聊天到设计文件末尾。
